# 0001. 记录级同步取代整包快照

- **状态**：已采纳
- **决策时间**：2026-08 中旬（回填记录）
- **关联**：server/db.ts（records 表 + 拆包迁移）、src/services/syncManager.ts、archive/v4.2-snapshot-sync.md

## 背景

v4.2 整包快照下，两台设备并行使用时后推整包直接覆盖前推整包——间隙里的任何编辑都被抹掉，
冲突粒度是整个数据集，自用双设备也不可接受。

## 决定

每条数据独立成记录 `{c, id, data, rev}` 落 `records` 表（主键 `(user_id, collection, record_id)`），
服务端逐条 LWW 裁决（表内 rev_time ≥ 推来 rev 则拒该条）；客户端维护内存基线 `lastSyncedMap`，
diff 出变更集上行。服务端保持"哑仓库"：不解析业务字段，data 整存整取。
一次性迁移：旧 snapshots 按用户拆包成记录行，拆完清空快照表数据。

## 后果

- (+) 冲突粒度从数据集细化到单条记录；删除可用墓碑表达；传输增量化的基础就此奠定。
- (+) 服务端与业务字段解耦：加字段/加集合零服务端改动。
- (-) 引入基线管理、墓碑生命周期、集合注册表等一整套客户端状态机复杂度。
- (-) 依赖"同 id 记录在集合中唯一"这一隐式约束（后来确曾被违反，见 2026-08-28 修复）。

## 被否决的备选

- **继续整包 + updatedAt 时间戳拒绝旧包**：粒度仍是整包，双设备并行编辑无解。
- **引入第三方同步引擎**（当时未选，2026-08-28 重新评估仍维持）：都要求专用服务端，
  推翻零依赖形态；且记录级 LWW 已足够匹配"单用户多设备、覆盖式修改"的场景。
