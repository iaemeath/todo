# 0002. 双时间戳分工：rev 管裁决、recv_time 管游标

- **状态**：已采纳
- **决策时间**：2026-08 中旬（回填记录）
- **关联**：server/sync.ts（push/pull）、src/services/syncManager.ts 头注、CLAUDE.md §4

## 背景

多设备时钟不可信（手动机器偏差、时区错乱），但既要做"谁的新谁赢"的裁决，
又要做"绝不漏数据"的增量拉取——单一时间戳无法同时安全承担两个职责。

## 决定

- `rev`（= 记录内嵌 revTime，**客户端时钟**）：只用于 LWW 裁决方向。时钟偏差的最坏结果
  只是"几乎同时的编辑选错了赢家"，这是 LWW 语义本身接受的。
- `recv_time`（**服务端时钟**）：只用于 pull 游标。服务端单调可靠，保证增量不漏。

## 后果

- (+) 客户端时钟漂移不会造成漏数据；裁决与服务端完全解耦。
- (-) 同一记录存两个时间戳，语义纪律靠约定维持——混用即出 subtle bug，已写入 CLAUDE.md 铁律。
- (-) rev 偏差场景下裁决可能反直觉（旧钟设备的编辑被覆盖），自用场景可接受。

## 被否决的备选

- **统一用服务端时间裁决**：需要服务端写时读改或 HLC，复杂度上升；且客户端离线编辑时长
  无法反映在裁决里（离线 1 小时的编辑会被在线的新编辑判负——但这本就是 LWW 语义，可接受，
  裁决必须用客户端时钟才有"编辑时刻"含义）。
- **逻辑时钟（Lamport/HLC）**：正确性更强，但对个人 todo 场景是过度设计。
