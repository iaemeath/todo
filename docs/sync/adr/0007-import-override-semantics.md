# 0007. 文件导入 = "备份为准"覆盖语义（revTime 复活 + 差集墓碑）

- **状态**：已采纳
- **决策时间**：2026-08 下旬确立，2026-08-28 单测加固修复
- **关联**：src/services/syncManager.ts（importBundle）、tests/sync-manager.test.ts

## 背景

文件导入（备份回滚）与增量同步并存时，语义必须回答两个问题：包里没有的本地数据怎么办？
本地已删除而包里有的记录怎么办？早期实现曾出现"导入后云端旧记录复活混入"的不一致。

## 决定

importBundle 是**整体覆盖**语义：

1. 包内记录统一打 `revTime=now` 并清除墓碑（复活）——"本机所见即真相"，作为新修订上行；
2. **差集墓碑**：本地有（活跃）而包内没有的 tasks/schedules 打墓碑（revTime=now）随推送上行，
   否则下次全量拉取时云端旧记录会复活混入；
3. 已墓碑且不在包内的记录**不重打**（幂等，避免无谓上行）；
4. 基线 `lastSyncedMap` 整体作废 → 下轮全量 diff 上行；
5. usage 是追加流水不参与差集墓碑（按 id 合并无裁决危害）。

2026-08-28 修复：复活路径必须剔除旧墓碑对象——同 id 重复入列时，collectAll 的 Map
后写覆盖先写，旧墓碑会反向覆盖复活版并推上云端，"导入复活已删任务"静默失效。

## 后果

- (+) 导入语义可预测："导入后本机 = 备份内容"，且登录态下 ~30s 内传播到云端与其他设备。
- (-) 与「云端恢复」同为整体覆盖，连用会互相踩（UI 警示 + CLAUDE.md 铁律）。
- (-) 差集墓碑使导入后第一轮推送变大（活跃 + 墓碑全集），自用规模无碍。

## 被否决的备选

- **合并式导入（包与本地取并集）**：语义模糊，"导入备份"的用户预期就是回到备份状态。
- **导入走 force pull 通道**：覆盖方向反了——用户要的是"文件覆盖云端"，不是"云端覆盖本地"。
