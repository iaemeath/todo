# 0010. 推送调度：前沿立即 + 后沿 2s 固定节流微批

- **状态**：已采纳
- **决策时间**：2026-08-28（提交 7450811）
- **关联**：src/services/syncManager.ts（PUSH_LEADING_GAP_MS、schedulePush/scheduleTrailingPush）、tests/sync-manager.test.ts

## 背景

原 30s 纯后沿防抖下，单设备编辑要等 30s 才上云（对端 ~31s 才可见）——SSE 只加速了
"服务器到对端"半程，"本机到服务器"半程仍是防抖节奏。而裸"编辑即推"又会被爆发操作
（导入数百条、拖拽排序重打整象限 order）放大几十倍请求量，顶到 keepalive 60KB 与 30 次/分限流。

## 决定

以 `lastPushedAt`（上次**成功**推送时刻）驱动双沿调度：

- **前沿**：距上次成功推送 >30s 的首个变更**立即推**——单次编辑秒级上云；
- **后沿**：刚推过/推送在途时进 **2s 固定节流窗**合并。固定窗（窗内不重置）而非纯防抖：
  持续编辑下滞后有 2s 上界，不会无限饿死；
- **失败有界重试**：前沿失败转后沿补一枪，仍失败停手——等下一次变更（前沿条件已重新满足）
  或兜底轮询，离线期不空转；
- keepalive/手动/兜底推送成功同样刷新 `lastPushedAt`，避免双推；`stopSync` 清零。

## 后果

- (+) 端到端：单设备编辑 → ~1s 上云 → SSE → 对端 ~1s 可见（原 ~31s）。
- (+) 爆发操作请求数 = 爆发时长/2s + 1，有上界。
- (-) `lastPushedAt` 是内存态：刷新后首轮推送（startSync 全量）重新满足前沿，语义自洽，
  无持久化必要。
- (-) 窗内变更合并意味着极小概率"最后一次编辑后 2s 才上云"，对 todo 场景无感。

## 被否决的备选

- **纯前沿（每次变更即推）**：爆发放大请求量，违背限流预算。
- **纯后沿缩短到 2s**：等于回到防抖老路，30s 空窗问题依旧；且高频重置计时器在持续编辑下饿死推送。
- **每次变更全量推**：数据量放大，与记录级 diff 设计相悖。
